# BMO RFC-0003 — Text Model (v0.3.2-alpha, DRAFT)

Status: **DRAFT**, depends on RFC-0001 + RFC-0002. Defines paragraphs,
runs, lists and styles. Shaping, line-breaking and pagination are the
RENDERER's job (separation per the BMO architecture); this document
defines what is stored and what is guaranteed about it.

## 1. Compatibility note

RFC-0002 reserved `paragraph`/`run`/… while `hello.bmo` used a generic
`text` kind. Rule: **`text` is a legacy alias** — body `{text: tstr,
lang?: tstr}`, validated like `note`. Writers v0.3+ MUST emit
`paragraph`+`run`; readers MUST accept `text` forever.

## 2. Storage principles

* **Logical order.** Text is stored in logical (reading) order, never
  visual order. `dir` metadata (§4) tells the renderer which way it runs.
* **Unicode.** Runs MUST be valid UTF-8 (enforced by the container's
  CBOR strings). NFC is RECOMMENDED on write, never required on read.
* **Paragraph boundary = object boundary.** A run MUST NOT contain
  U+2029 (PARAGRAPH SEPARATOR) — validators reject it. `\n` inside a run
  is a soft line break and is allowed. U+FFFE/U+FFFF SHOULD NOT be emitted.
* **No layout numbers.** No x/y/width/font-metrics in this RFC. Spacing
  hints ride in opaque maps and MUST be preserved, never required.

## 3. Kinds and bodies

### 3.1 `paragraph`

```text
{
  align?: "start"|"end"|"left"|"right"|"center"|"justify" (default "start"),
  dir?: "auto"|"ltr"|"rtl" (default "auto"),
  list?: { id: tstr, level: uint 0..8 },
  style?: { $ref },
  spacing?: map?   # opaque hints, preserved
}
```

* Children MUST all be `run` (empty paragraph allowed).
* `list.id` MUST match a `list-def` id present in the same file, else
  `STRUCTURE_INVALID`. `level` > 8 is invalid.

### 3.2 `run`

```text
{
  text: tstr (REQUIRED, may be ""),
  lang?: tstr (BCP47, non-empty),
  script?: tstr (exactly 4 letters, e.g. "Arab", "Latn"),
  style?: { $ref }
}
```

* Parent kind MUST be `paragraph` (runs never float).
* `script` of any other length is `STRUCTURE_INVALID`.

### 3.3 `list-def`

```text
{
  id: tstr (REQUIRED, non-empty),
  style?: tstr, start?: uint, text?: tstr,             # level 0
  levels?: [{ level: uint 1..8, style?: tstr,
              start?: uint, text?: tstr }]             # overrides for levels 1..8
}
```

* `id` MUST be unique file-wide (duplicate → `STRUCTURE_INVALID`).
* `levels`, when present, MUST be an array with at most one entry per level.
  `style`, `start`, and `text` describe the numbering format, initial value,
  and marker pattern (for example, `decimal`, `5`, and `%1.`). A missing
  per-level property inherits the level-0 value, except `start`, which
  defaults to `1`.

### 3.4 `style`

```text
{ name?: tstr, basedOn?: { $ref }, run?: map?, para?: map? }
```

* `basedOn` target existence is enforced by R6 (it is a `$ref`).
  `run`/`para` submaps are renderer-interpreted and opaque here.

### 3.5 `table` / `row` / `cell` (added v0.3.1 — DOCX interchange needs them)

```text
table { cols?: uint, style?: { $ref } }   # children ⊆ row; parents ∈ document|section|page|slide|cell
row   { h?: uint }                        # children ⊆ cell; parent MUST be table
cell  { gridSpan?: uint ≥1 (default 1) }   # children ⊆ paragraph|table (empty = empty cell); parent MUST be row
```

* Membership: `page` and `slide` allowed-children gain `table`.
  A cell MAY contain paragraphs and nested tables; a nested table follows
  the same table/row/cell rules. Documents/sections stay unrestricted.
* Rationale: document tables hold block content (paragraphs), unlike
  sheet cells which are inline values (RFC-0005). Two models on purpose —
  conflating them caused decades of Word↔Excel paste bugs elsewhere.

## 4. Direction model

* Paragraph `dir`: `auto` (renderer decides from first strong character
  per UBA), `ltr`, `rtl`. Run-level direction is derived from
  `script`/`lang`, with no per-run override in v0.3 (explicit embeddings
  via Unicode controls are permitted but SHOULD be avoided in favor of
  this metadata).
* Numbers, neutral characters and nested embeddings follow UAX #9 in the
  renderer. Two readers may rasterize differently; they MUST agree on
  the stored bytes and the paragraph/run tree — that is the conformance
  boundary of this RFC.

## 5. Chunk mapping, features

* v0.x writers MUST use `GENERIC_OBJECT`. (Typed text chunks live in the
  `0x0020–0x002F` range when a future RFC needs binary packing; readers
  will support both per RFC-0002 §8.)
* `DOCUMENT.features` advertises `"text.v1"`.

Exercises: LTR + RTL + mixed-direction runs, centered alignment,
style references, list membership, script/lang metadata.

## 7. Conformance

* Bodies validated per §3 (see `tests/conformance/domains_check.py`,
  `core/rust/src/domains.rs`): bad `align`, U+2029 in runs, bad
  `script` length, missing list id, duplicate list id, run outside
  paragraph → `STRUCTURE_INVALID`.
* Round-trip: unknown body keys, `spacing` hints and future `style`
  subkeys survive appends byte-exact.
