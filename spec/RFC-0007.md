# BMO RFC-0007 — Security (v0.7.2-alpha, DRAFT)

Status: **DRAFT**, depends on RFC-0001 (§9–§10). This document pins down
the encryption envelope, key management profiles, signature verification
and the threat model. It invents no cryptography — suite IDs only name
standard algorithms with exact parameters.

## 1. Cipher suites (encryption IDs, high u16 of `codec`)

| ID | Name | Nonce | Tag | Stored payload layout |
|----|------|-------|-----|-----------------------|
| 1 | AES-256-GCM (SP 800-38D) | 12 B random | 16 B | `nonce\|\|ciphertext\|\|tag` |
| 2 | ChaCha20-Poly1305 (RFC 8439) | 12 B random | 16 B | `nonce\|\|ciphertext\|\|tag` |
| 3 | XChaCha20-Poly1305 | 24 B random | 16 B | `nonce\|\|ciphertext\|\|tag` |

* Order of operations is fixed: **compress-then-encrypt**. Readers
  verify trailer CRC (over ciphertext) → decrypt + verify tag → then
  decompress. Tag failure → `AUTH_FAILED`; readers MUST NOT return
  partial plaintext, MUST NOT fall back to another suite.
* Nonces MUST come from a CSPRNG and MUST never repeat for one content
  key. v0.7 uses one random 32-byte content key per file; per-chunk key
  derivation (HKDF) is RECOMMENDED for future profiles, not required —
  unique nonces already give GCM/ChaCha safety.
* `decoded_len` is the plaintext size AFTER decrypt+decompress;
  `stored_len` includes nonce+tag overhead. Framing check:
  `stored_len == nonce_len + ciphertext_len + 16`.

## 2. SECURITY chunk (0x0007)

Present iff any chunk is encrypted (or anticipated). MUST itself be
unencrypted (`ENCRYPTED` flag MUST be 0) so readers can discover how to
ask for keys. Canonical CBOR:

```text
{
  "encrypted": bool,
  "contentAlg": tstr,     # informational; per-chunk codec is authoritative
  "keyWrap": {
    "method": "none"       # TEST VECTORS ONLY — readers SHOULD warn
            | "password-argon2id" | "kms" | "cert",
    "params": {...},       # method-specific (see below)
    "wrappedKey": bstr,    # for password/cert; absent for kms
    "kmsUri": tstr         # for kms only
  }
}
```

### 2.1 `password-argon2id` (RFC 9106)

`params = {salt: bstr(16), time: 1..8, mem: 8192..1048576 (KiB),
par: 1..8}`. Readers MUST reject parameters outside these bounds
(`STRUCTURE_INVALID`, not silent clamping). KEK → AES-KW unwrap of the
32-byte content key.

### 2.2 `kms` / `cert`

Store references (`kmsUri`, certificate fingerprint + algorithm), never
key material. Offline readers return `NEED_KEY` (fail closed); they MUST
NOT cache plaintext beyond the session.

## 3. Signatures (0x0008)

Schema per RFC-0001 §6.5. The signed bytes are EXACTLY:

```text
canonicalBytes = DeterministicCBOR({
  "magic": "BMO1",
  "fileId": bstr(16),
  "txn": uint,                       # covered transaction
  "objects": { decimal-id: sha256(decoded payload) }   # sorted
})
canonicalHash = SHA256(canonicalBytes)
```

Covered set: `DOCUMENT` + all `CRITICAL` + `GENERIC_OBJECT` +
`ASSET_DATA` (+ tables). Excluded: directory, root, `SECURITY`,
`SIGNATURE`s, footers. Algorithm IDs: `"Ed25519"`, `"ECDSA-P256-SHA256"`,
`"RSA-PSS-SHA256"`. Multiple `SIGNATURE` chunks = multiple signers over
the same hash. Timestamps are informational (no TSA in v0.7).
ECDSA signatures use ASN.1 DER; RSA-PSS signatures are raw RSA octets,
with MGF1-SHA256 and a 32-byte salt. Both algorithms use SHA-256 over
the 32-byte `canonicalHash`; Ed25519 signs that hash directly. Trusted
public keys are provisioned out of band as DER SubjectPublicKeyInfo for
ECDSA/RSA (Ed25519 uses its raw 32-byte public key).
Verification of `hello.bmo` pins the construction:
`canonical(hello.bmo) = ea6db170f6709d45…398e22ab5f` (test locks it).

## 4. Threat model (what BMO promises)

* **At rest:** AES-GCM/ChaCha confidentiality + integrity per chunk.
  Attacker with the file but not the key learns: file size, chunk count,
  chunk sizes, modification txn cadence (traffic-shape metadata is NOT
  hidden — documented, not a bug).
* **In transit:** file is self-protecting; signatures prove origin +
  integrity, never trust (key distribution is out of scope, BYO-PKI).
* **Malicious files:** no execution on open (RFC-0001 §15); all lengths
  pre-checked (§14); decompression ratio capped at 64:1 per chunk unless
  the `ARCHIVE` profile explicitly allows more with user confirmation.
* **Non-goals:** hiding access patterns, deniability, post-quantum suites
  (registry reserved, migration path via suite IDs).

## 5. Test vectors

* `tests/golden/encrypted.bmo` — 815 bytes,
  `sha256=0fab8259ab54a49d…672baadf`: ChaCha20-Poly1305 chunk,
  `method:none` envelope, deterministic key/nonce. Suite asserts:
  decrypt round-trip, every-byte tamper rejected, wrong-key/wrong-nonce
  fail closed, framing `stored == 12 + plain + 16`.
* Cipher *implementation* in the test harness is pure-Python RFC 8439,
  but it is proven against the **official RFC 8439 §2.8.2 vector**
  (key/nonce/aad/plaintext/ciphertext/tag byte-exact) — interop holds
  for the construction; production SDKs MUST still use audited libraries
  (timing, not vectors, is what the warning is about).
* `tests/golden/signed.bmo` — 872 bytes: Ed25519 signature over the
  §10 canonical hash. The harness Ed25519 is proven against **RFC 8032
  §7.1 TEST 1..3** (pubkey+signature byte-exact); the suite recomputes
  the canonical hash and verifies (plus tamper rejection).
* Argon2id is proven against the **official phc GENKAT trace**
  (`kats/argon2id`, m=32/t=3/p=4, source sha256
  `ba05643e504fc5778dda99e2d9f42ebe7d22ebb3923cc719fd591b1b14a8d28d`):
  all 96 memory blocks match the reference dump block-for-block across
  all 3 passes, plus the initial hash and final tag — parsed to the
  digest manifest `tests/vectors/reference/argon2id_kat_v19_m32_t3_p4.json`
  and asserted by `test_crypto.py` (`argon2id_blocks`). The pure-Python
  harness is additionally cross-checked against the reference C
  implementation over a parameter matrix (`test_password.py`,
  `kdf_cross_impl`).
* Password wrap (Argon2id → RFC 3394 AES-KW) is implemented in the
  Python kit via `cryptography`: RFC 3394 §4.1/§4.6 official vectors,
  plus `tests/golden/password.bmo` (KEK, wrapped key, plaintext all
  pinned). Rust core has no KDF/key-wrap yet and fails closed
  (`NEED_KEY`) on wrapped files.
* Builds without a cipher (e.g. the current `bmo-core`) MUST open
  encrypted files with a clean `UPGRADE_REQUIRED` — never garbage.
