# BMO RFC-0001 — Binary Container (v0.1.0-alpha, DRAFT)

Status: **DRAFT 0.1.0-alpha** — experimental. No compatibility guarantee
across 0.x. This document is normative for the container layer only.
Document-model layers are RFC-0002+.

Scope: byte-level layout of `.bmo` files: magic, header, chunks,
indexes, compression, integrity, encryption envelope, signatures,
transactions / append-only, footer / recovery, canonical encoding,
limits, versioning and forward-compatibility rules.

Language-independent. The Rust core is the reference implementation,
but this text — not any code — is authoritative. Any implementation
that passes the conformance suite in `tests/conformance` is conformant,
regardless of language.

References (normative dependencies, not vendored):
CBOR RFC 8949 + deterministic encoding, Zstandard RFC 8878,
DEFLATE RFC 1951 / zlib RFC 1950, CRC32C (Castagnoli, RFC 3720 App. B),
SHA-256 FIPS 180-4, AES-GCM NIST SP 800-38D, ChaCha20-Poly1305 RFC 8439,
XChaCha20-Poly1305 draft-arciszewski-xchacha, Ed25519 RFC 8032,
Argon2id RFC 9106, HKDF RFC 5869, UTF-8 RFC 3629, UUID RFC 9562.

Conformance keywords: MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT /
SHOULD / SHOULD NOT / RECOMMENDED / MAY / OPTIONAL per RFC 2119 / 8174.

---

## 1. Design principles (non-negotiable)

1. **Spec first, code second.** If code and this text disagree, this text wins.
2. **Container ≠ model ≠ renderer.** This RFC defines only the container:
   how bytes are stored, found, verified, decrypted. What a paragraph or
   a formula *means* is RFC-0002+.
3. **Random access + huge files.** Opening slide 700 of a 1.8 GB file MUST
   NOT require reading the whole file. All object locations go through
   the Root Index → Object Directory → chunk offset chain (§7–§8).
4. **Crash safety.** Power loss during save MUST leave the previous valid
   state readable (§11). Single-file atomic commit via footer replacement.
5. **Append-only / copy-on-write.** An edit writes new chunks + new index
   + new footer; it MUST NOT rewrite unchanged bytes in place (except
   compaction, §11.4).
6. **Integrity by default, crypto agility.** Every chunk carries CRC32C;
   assets carry SHA-256; encryption/signature algorithm IDs are
   extensible registries, never hard-coded (§9–§10).
7. **Forward compatibility.** Old readers MUST skip + preserve unknown
   ancillary chunks byte-exact (§13). New features MUST NOT silently
   corrupt old files.
8. **No executable content in 1.0 scope.** A `.bmo` file MUST NOT cause
   code execution on open. Automation (if ever) lives outside this RFC,
   sandboxed (e.g. WASM), never inline native code (§15).

## 2. Primitives

### 2.1 Endianness and integers

* All fixed-width integers are **little-endian (LE)**.
* Types: `u8, u16, u32, u64, i64`. No varints at container level (keeps
  `mmap` + binary search trivial). CBOR inside payloads MAY use its own
  ints, but offsets in §7–§8 are always fixed LE.
* `u64` file offsets: top 16 bits MUST be zero (max addressable
  2^48-1, §14). Writers MUST reject larger values; readers MUST reject
  files containing them with `LIMIT_EXCEEDED`, never wrap.
* Times: `i64` LE, milliseconds since Unix epoch (UTC). Range
  0001-01-01..9999-12-31. `0` means "unknown / test vector".
* Floats do NOT appear at container level. Inside CBOR payloads use
  RFC 8949 preferred float encoding (shortest that round-trips).

### 2.2 Checksums and hashes

* **CRC32C (Castagnoli)**: polynomial `0x1EDC6F41`, reflected `0x82F63B78`,
  init `0xFFFFFFFF`, xorout `0xFFFFFFFF`. Test: `CRC32C("123456789") = 0xE3069283`.
  Used per chunk header + per stored payload + file header + footer.
  Rationale: hardware acceleration (SSE4.2/ARMv8), fast corruption
  detection. NOT cryptographic.
* **SHA-256** (FIPS 180-4): used for assets, content addressing, and the
  signature canonical hash. `SHA256("") = e3b0c44...`.
* Empty payload CRC: `CRC32C(b"") = 0x00000000` (init ^ xorout).

### 2.3 UUIDs / file IDs

* `file_id`: 16 bytes, SHOULD be UUIDv7 (RFC 9562) randomly generated per
  new file. Test vectors use fixed bytes (see §16). `DOCUMENT.docId`
  MUST equal header `file_id`, else file is `CORRUPT`.

### 2.4 Strings

* All text at container level: UTF-8 (RFC 3629), MUST be valid UTF-8,
  MUST NOT contain lone surrogates. Comparison: byte-wise (Unicode
  normalization is a model-level concern, RFC-0003).

### 2.5 Canonical CBOR profile (control structures only)

Container control payloads (`DOCUMENT`, `ASSET_TABLE`, `SECURITY`,
`SIGNATURE`, `GENERIC_OBJECT` wrapper in v0.1) use CBOR (RFC 8949) with
**deterministic encoding**:

* shortest-form ints, definite lengths only, sorted keys (lexicographic
  by encoded key bytes), no duplicate keys, no indefinite items, no
  NaN, preferred float size, UTF-8 text (no chunked strings).
* Writers MUST emit this form. Readers MUST accept any valid CBOR but
  SHOULD re-emit canonical form on save (so hashes stabilize).
* Bulk document content (text runs, cell grids, slide trees) is NOT
  required to be CBOR in future RFCs — only control structures here.

## 3. File overview

```text
offset 0:
+------------+  64 bytes, fixed
| FILE HEADER|  magic "BMO\x1A", versions, flags, file_id, crc, time
+------------+
| chunk 0    |  40-byte header + stored_payload + 4-byte trailer
| chunk 1    |
| ...        |  chunks in write order (NOT sorted; directory sorts)
| chunk N    |  includes OBJECT_DIRECTORY + ROOT_INDEX chunks
+------------+
| FOOTER     |  64 bytes, fixed; points to ROOT_INDEX; commit marker
+------------+  EOF
```

* Minimum valid file: 64 (header) + ≥1 chunk + 64 (footer) = ≥172 bytes
  (real minimum larger; see §16).
* Magic allows `file(1)` + fast reject. Header/footer sizes are fixed
  (64 each) in v0.x–1.x so recovery scanning is trivial. Future major
  versions MAY define larger headers but MUST keep first 8 bytes
  (`magic + major`) at the same offsets.

## 4. File header (64 bytes, fixed)

| Off | Size | Field | Value / rule |
|-----|------|-------|--------------|
| 0 | 4 | `magic` | `42 4D 4F 1A` = `B M O SUB`. `SUB` stops accidental text display (same trick as PNG). MUST match exactly. |
| 4 | 2 | `format_major` u16 LE | `0` for this draft. |
| 6 | 2 | `format_minor` u16 LE | `1` for this draft. |
| 8 | 2 | `header_length` u16 LE | MUST be `64`. |
| 10 | 2 | `header_version` u16 LE | MUST be `1`. |
| 12 | 4 | `flags` u32 LE | bit0 `ENCRYPTED` (any chunk encrypted), bit1 `SIGNED` (≥1 signature), bit2 `ARCHIVE` (archive profile requested), bits 3–31 reserved, MUST be 0 on write. Readers MUST ignore unknown flag bits for forward compat but MUST still enforce chunk-level checks. Header flags are advisory; chunk flags are authoritative. |
| 16 | 16 | `file_id` | 16 raw bytes (UUIDv7 RECOMMENDED). |
| 32 | 4 | `header_crc` u32 LE | `CRC32C(bytes[0..32] \|\| bytes[36..64])` — i.e. whole header with this field zeroed/skipped. |
| 36 | 8 | `created_ms` i64 LE | creation time, `0` = unknown/test. |
| 44 | 20 | `reserved` | MUST be zero on write. Readers MUST ignore (not CRC-covered, allows future use without breaking old CRC logic — old readers ignore, new readers define sub-version). |

Validation order on open: check size ≥128 → check `magic` → check
`header_length==64 && header_version==1` → check `format_major`
supported (§13) → verify `header_crc` → copy `file_id`.

## 5. Chunks

### 5.1 Chunk header (40 bytes) + payload + trailer (4 bytes)

On-disk chunk = `header(40) + stored_payload[stored_len] + trailer(4)`.

| Off (rel) | Size | Field | Rule |
|-----------|------|-------|------|
| 0 | 4 | `chunk_type` u32 LE | registry §5.3. `0x0000` MUST NOT appear. |
| 4 | 2 | `chunk_version` u16 LE | per-type version, starts at `1`. Reader with lower version follows §13. |
| 6 | 2 | `chunk_flags` u16 LE | §5.2. |
| 8 | 8 | `object_id` u64 LE | stable ID, `0` = "no object" (system chunks MAY use 0; model objects MUST use ≠0). |
| 16 | 8 | `stored_len` u64 LE | bytes on disk after compression+encryption (nonce+tag included). MUST be ≤ 2^32-1. MUST equal actual remaining bytes before trailer. |
| 24 | 8 | `decoded_len` u64 LE | bytes after decrypt+decompress (plaintext control bytes). MUST be ≤ 2^32-1. If no codec, MUST equal `stored_len` minus crypto overhead (0 if plain). |
| 32 | 4 | `codec` u32 LE | low u16 = compression id, high u16 = encryption id (§9). `0` = plain. |
| 36 | 4 | `header_crc` u32 LE | `CRC32C(header[0..36])`. |

Trailer: `payload_crc u32 LE = CRC32C(stored_payload)` (ciphertext if
encrypted, compressed bytes if compressed-only).

Read pipeline (MUST be in this order):

```text
read header → verify header_crc → check lengths ≤ limits →
read stored_payload + trailer → verify payload_crc →
if ENCRYPTED: decrypt (→ intermediate) else intermediate = stored_payload →
if COMPRESSED: decompress (→ decoded, MUST be exactly decoded_len bytes) →
dispatch by chunk_type
```

Write pipeline is the reverse (`serialize → compress → encrypt → crc`).

`decoded_len` + `stored_len` let readers pre-allocate and detect
truncation without decompressing.

### 5.2 Chunk flags (u16)

* `0x0001 COMPRESSED` — payload compressed per `codec.compression`.
* `0x0002 ENCRYPTED` — payload encrypted per `codec.encryption`. If set,
  `SECURITY` chunk MUST exist (unencrypted) and `codec.encryption != 0`.
* `0x0004 HAS_OBJECT_ID` — `object_id != 0` and meaningful. If clear,
  `object_id` MUST be 0.
* `0x0008 CRITICAL` — if set and `chunk_type` unknown to reader, MUST
  refuse open (`UNKNOWN_CRITICAL`). If clear and unknown, MUST skip +
  preserve (§13).
* `0xFFF0` reserved. Writers MUST write 0. Readers: preserve on
  round-trip; if `CRITICAL==1` and any reserved bit set → MUST refuse
  (conservative); if `CRITICAL==0` → MUST ignore + preserve.

### 5.3 Chunk type registry (u32)

```text
0x0000  RESERVED_INVALID      MUST NOT appear; readers MUST reject.
0x0001  DOCUMENT              control, CBOR, CRITICAL=1, HAS_OBJECT_ID=0 (file-level).
0x0002  OBJECT_DIRECTORY      system index, binary, CRITICAL=1, object_id=0.
0x0003  ROOT_INDEX            system index, binary, CRITICAL=1, object_id=0.
0x0004  ASSET_TABLE           control, CBOR, CRITICAL SHOULD be 1 if assets exist.
0x0005  ASSET_DATA            raw bytes, ancillary (CRITICAL=0 RECOMMENDED so old readers can skip media).
0x0006  INDEX_SECONDARY       binary, ancillary (CRITICAL=0) unless a future RFC promotes it.
0x0007  SECURITY              control, CBOR, CRITICAL=1 if present, MUST be unencrypted.
0x0008  SIGNATURE             control, CBOR, ancillary (CRITICAL=0) — a reader MAY verify or ignore, but MUST preserve.
0x0010  GENERIC_OBJECT        v0.1 model holder, CBOR map {kind,parent,body}; CRITICAL=1, HAS_OBJECT_ID=1.
0x0020–0x00FF  RESERVED       for RFC-0002..0006 (text/layout/graphics/spreadsheet/presentation). Readers MUST treat as unknown per flags.
0x0100–0x7FFF  EXTENSION      registry-controlled. Unknown → flags rule applies. Writers MUST list used extensions in DOCUMENT.requiredExtensions or optionalExtensions.
0x8000–0xFFFF  PRIVATE/EXPERIMENTAL  MUST be ancillary (CRITICAL=0), MUST be preserved, MUST NOT appear in requiredExtensions of a conformant file.
```

`chunk_version`: per-type, starts at 1. Minor additions MUST be
backward-compatible within same version (additive optional CBOR keys,
never repurpose bytes). Breaking layout change REQUIRES new
`chunk_type` or major format bump.

### 5.4 Object IDs (u64)

* `0` reserved = "no object". All model objects use `≠0`.
* IDs are stable across saves (copy-on-write creates a *new chunk* for
  the same `object_id`; the directory is updated to point at the new
  offset — history preserved if previous footers kept).
* v0.1 allocation: `1` = document root (`GENERIC_OBJECT` kind
  `"document"`), then monotonically increasing per new object. Writers
  MUST NOT reuse IDs of deleted objects within the same file history
  (tombstone in directory until compaction).
* Readers MUST reject duplicate `object_id` entries in a single
  `OBJECT_DIRECTORY` (`DUPLICATE_OBJECT_ID`).
* Future RFCs MAY partition the u64 space (e.g. high bits = domain);
  v0.1 readers MUST treat IDs as opaque.

## 6. Control payload schemas (canonical CBOR)

### 6.1 DOCUMENT (0x0001)

CBOR map, keys (text), deterministic encoding:

```text
{
  "bmoMajor": uint, "bmoMinor": uint,        # MUST equal header major/minor
  "minMajor": uint, "minMinor": uint,        # minimum reader version required
  "docType": tstr,   # "generic" in v0.1; future: "document","spreadsheet","presentation","database","notebook",...
  "docId": bstr(16), # MUST equal header file_id
  "created": int, "modified": int,           # ms since epoch, 0 = unknown
  "features": [* tstr],                      # e.g. ["compression.zstd","encryption.aes-gcm"]
  "requiredExtensions": [* tstr],            # e.g. ["chart@2"]; unknown entry → MUST refuse
  "optionalExtensions": [* tstr],
  "metadata": {* tstr => any}                # title/author/... model-level, preserved verbatim
}
```

Required keys: `bmoMajor,bmoMinor,minMajor,minMinor,docType,docId`.
Writers MUST set `minMajor/minMinor` to the oldest reader that can open
the file (usually same as file version unless using new extensions).

### 6.2 GENERIC_OBJECT (0x0010, v0.1 holder)

Until RFC-0002..0006 define typed objects, model objects use:

```text
{
  "kind": tstr,    # e.g. "document","page","text","style" (see §16 example)
  "parent": uint,  # object_id of parent, 0 = root
  "body": any      # kind-specific CBOR; v0.1: { "text": tstr, ... }
}
```

Readers MUST preserve unknown `kind` values (forward compat).

### 6.3 ASSET_TABLE (0x0004) + ASSET_DATA (0x0005)

Content-addressed storage. Large binary (images/audio/video/fonts) lives
in `ASSET_DATA` raw bytes; the table maps hash → metadata.

`ASSET_TABLE` CBOR: map `sha256(bytes 32) => { "size": uint,
"mime": tstr, "chunks": [* uint(object_id of ASSET_DATA chunks in order)] }`.
Split rule: assets larger than `2^32-1` MUST be split into multiple
`ASSET_DATA` chunks; smaller assets SHOULD be single-chunk. Writers
SHOULD dedup: same SHA MUST reuse table entry (multiple parents
reference same hash). Readers MUST support shared references.

`ASSET_DATA` payload = raw bytes (already codec-processed at chunk
layer; no inner framing). `object_id` SHOULD be unique per slice.

### 6.4 SECURITY (0x0007)

Present iff any chunk encrypted (or file anticipates encryption).
MUST itself be unencrypted (`ENCRYPTED` flag MUST be 0).

```text
{
  "encrypted": bool,
  "contentAlg": tstr,   # e.g. "AES-256-GCM" (informational; per-chunk codec authoritative)
  "keyWrap": {
    "method": tstr,  # "none" (TEST ONLY) | "password-argon2id" | "kms" | "cert"
    "params": {...}, # e.g. {"salt": bstr, "time": 3, "mem": 65536, "par": 1} for argon2id
    "wrappedKey": bstr,  # present for password/cert; absent for kms
    "kmsUri": tstr       # present for kms
  }
}
```

* `method "none"` stores raw content key — MUST NOT be used outside
  tests/conformance vectors; readers SHOULD warn.
* Password: Argon2id (RFC 9106) → KEK → AES-KW wrap of 32-byte content
  key. Params MUST be stored to allow re-derivation.
* Per-chunk encryption uses the *content key* directly with a fresh
  random nonce per chunk (§9.2). Key derivation per chunk (HKDF) is
  RECOMMENDED for future profiles but NOT required in v0.1 (unique
  nonces suffice for GCM/ChaCha safety).

### 6.5 SIGNATURE (0x0008)

```text
{
  "signer": tstr, "alg": tstr,  # "Ed25519" | "ECDSA-P256-SHA256" | "RSA-PSS-SHA256"
  "canonicalHash": bstr(32),    # SHA256(canonicalBytes per §10)
  "signature": bstr,            # over the 32-byte canonicalHash
  "timestamp": int,
  "coveredTxn": uint, "coveredRootOffset": uint
}
```

Multiple `SIGNATURE` chunks allowed (multiple signers). Excluded from
their own coverage (§10).

For ECDSA-P256-SHA256, `signature` is ASN.1 DER and the verifier MUST
use SHA-256 over the supplied 32-byte `canonicalHash` as the ECDSA
message digest. For RSA-PSS-SHA256, `signature` is the raw RSA signature
octet string, MGF1 uses SHA-256, and salt length is exactly 32 bytes.
Implementations receive trusted signer public keys out of band; keys are
not embedded in this chunk. ECDSA and RSA public keys use DER
SubjectPublicKeyInfo encoding at verifier APIs. Ed25519 signs the
32-byte `canonicalHash` directly.

## 7. Object Directory (0x0002, binary)

Payload (decoded bytes, LE):

```text
0  u32 version (=1)
4  u32 count (N)
8  u64 txn_id (MUST equal footer txn_id that points here)
16 N * entry[32]:
     0  u64 object_id
     8  u32 chunk_type
     12 u32 reserved (=0)
     16 u64 file_offset (of chunk header byte 0)
     24 u64 total_len (40 + stored_len + 4; allows skipping without parsing header)
```

* Entries MUST be sorted ascending by `object_id`, no duplicates.
* Every `HAS_OBJECT_ID` chunk in the file SHOULD have an entry; system
  chunks with `object_id==0` MAY be omitted (found via `ROOT_INDEX`).
* Deleted objects: writers SHOULD keep a tombstone entry with
  `file_offset = 0xFFFFFFFFFFFFFFFF` until compaction (lets readers
  distinguish "deleted" from "never existed" for sync/collab).
* Directory itself is a chunk (so it gets header+CRC); its offset is in
  `ROOT_INDEX`.

## 8. Root Index (0x0003, binary)

Payload:

```text
0 u32 version (=1)
4 u32 index_count (M, secondary indexes; 0 allowed in v0.1)
8 u64 dir_offset (file offset of OBJECT_DIRECTORY header)
16 u64 dir_total_len (40 + stored + 4)
24 M * { u32 index_type, u32 reserved, u64 index_offset, u64 index_total_len }
   (24 bytes per entry; payload length MUST equal 24 + 24*M)
```

* `ROOT_INDEX` offset is in the `FOOTER` (§12). Chain:
  `FOOTER → ROOT_INDEX → OBJECT_DIRECTORY → object chunks`.
* Unknown `index_type` MUST be ignored (but preserved via its chunk).
* v0.1 defines no mandatory secondary index (`M=0` valid). Future:
  `0x01 KIND_INDEX`, `0x02 FULLTEXT`, etc.

## 9. Compression and encryption (codec u32)

`codec = (encryption_id << 16) | compression_id`.

### 9.1 Compression IDs (low u16)

* `0 NONE` — stored == decoded (modulo crypto overhead).
* `1 ZSTD` — RFC 8878, single frame per chunk, content-size SHOULD be
  present, no dictionary. Level is encoder choice (default 3
  RECOMMENDED). Decoder MUST support any valid frame.
* `2 DEFLATE` — zlib wrapper (RFC 1950) containing DEFLATE (RFC 1951).
  Decoder MUST support windowBits ≤15.
* `3–32767` reserved. `32768–65535` private/experimental.
* If `COMPRESSED` flag set, `compression_id MUST != 0`; if clear, MUST be 0.
  `decoded_len` is the decompressed size; mismatch → `CORRUPT`.

### 9.2 Encryption IDs (high u16)

* `0 NONE`.
* `1 AES-256-GCM` — 12-byte random nonce per chunk, 16-byte tag appended.
  Stored = `nonce(12) || ciphertext || tag(16)`.
* `2 ChaCha20-Poly1305` — same layout, 12-byte nonce.
* `3 XChaCha20-Poly1305` — 24-byte nonce, same tag.
* If `ENCRYPTED` set, `encryption_id MUST != 0` and `SECURITY` MUST exist.
  Nonces MUST be unique per (key, chunk-write) — use CSPRNG. Writers MUST
  NOT reuse nonces. Order: **compress-then-encrypt**. Reader: verify
  trailer CRC (ciphertext) → decrypt+verify tag (failure → `AUTH_FAILED`,
  MUST NOT return partial plaintext) → decompress if needed.
* Key management never invents crypto: standard algorithms only. Password
  KDF MUST be Argon2id; KMS/cert profiles store references, never keys
  in clear outside `method:none` test files.

## 10. Canonical bytes and signatures

To sign, hash a deterministic projection (so re-serialization without
semantic change verifies):

```text
canonicalBytes = DeterministicCBOR({
  "magic": "BMO1",
  "fileId": bstr(16),
  "txn": uint(coveredTxn),
  "objects": { tstr(decimal object_id) => bstr(sha256(decoded payload)) : sorted by numeric object_id }
})
canonicalHash = SHA256(canonicalBytes)
```

* Covered set: all `CRITICAL` + `DOCUMENT` + `GENERIC_OBJECT` +
  `ASSET_DATA` (by decoded hash) + `ASSET_TABLE` decoded hash.
  Excluded: `OBJECT_DIRECTORY`, `ROOT_INDEX`, `SECURITY` (key material),
  `SIGNATURE` themselves, `FOOTER`.
* Sign `canonicalHash` with signer key; store per §6.5. Verify by
  recomputing. Timestamp is informational (trust requires external TSA;
  not in v0.1).

## 11. Transactions, append-only, compaction

### 11.1 Commit protocol (writer MUST follow)

1. Assign `txn_id = prev_txn + 1` (genesis = 1).
2. Write new/changed object chunks + new `ASSET_*` if needed (with new
   offsets), `fsync` payload (advisory on all OSes).
3. Write new `OBJECT_DIRECTORY` (full snapshot of live + tombstone
   entries for this txn).
4. Write new `ROOT_INDEX` pointing at it.
5. Write new `FOOTER` (prev = old footer offset, root = new index
   offset, txn = new id), single 64-byte write + `fsync` directory/file.
   This write is the commit point.

Readers MUST open via the **last valid footer** only (§12.2). A crash
before step 5 leaves the old footer valid → old state intact. A torn
footer write is detected by magic/CRC and ignored (fall back).

### 11.2 Copy-on-write

Modified object with id `X` → new chunk with same `object_id=X` at new
offset; directory entry updated. Old chunk bytes remain (reachable via
old footers if history kept). Writers MUST NOT modify bytes in place.

### 11.3 Incremental saves

Small edits append only deltas + directory + index + footer. Opening
slide 700 reads: footer → root → directory (binary search `object_id`)
→ seek + read that chunk only.

### 11.4 Compaction / GC

A compactor MAY rewrite the file (new `file_id`? No — MUST preserve
`file_id`; new history chain with `prev = UINT64_MAX` = "compacted, no
history"). MUST preserve unknown ancillary chunks (§13) and MUST drop
only unreachable bytes + tombstones. SHOULD re-emit canonical CBOR.

## 12. Footer (64 bytes) + recovery

| Off | Size | Field |
|-----|------|-------|
| 0 | 4 | `footer_magic` = `42 4D 4F 46` (`B M O F`) |
| 4 | 2 | `footer_version` u16 (=1) |
| 6 | 2 | `footer_flags` u16 (bit0 `COMPACTED_HISTORY_LOST` if prev==MAX; rest reserved 0) |
| 8 | 8 | `root_offset` u64 (of ROOT_INDEX header) |
| 16 | 8 | `root_total_len` u64 (40+stored+4) |
| 24 | 8 | `txn_id` u64 (≥1, monotonic) |
| 32 | 8 | `prev_footer_offset` u64 (`0` = genesis, `MAX` = compacted, else offset of previous footer header) |
| 40 | 4 | `footer_crc` = `CRC32C(bytes[0..40])` |
| 44 | 16 | `reserved` (MUST be 0, ignored) |
| 60 | 4 | `footer_magic` duplicate (MUST equal bytes[0..4]) |

### 12.2 Open + recovery procedure (reader MUST implement)

1. If size < 128 → `TOO_SMALL`.
2. Validate file header (§4).
3. Read `footer_candidate = bytes[size-64..size]`; check both magics +
   `footer_crc` + `root_offset/len` within bounds. If valid → open via it.
4. Else (torn tail): backward scan up to `min(size, 16 MiB)` byte-by-byte
   for `FOOTER_MAGIC ... (60 bytes) ... FOOTER_MAGIC` with valid CRC and
   in-bounds root pointer. First (newest) valid hit wins. If none →
   `NO_VALID_FOOTER` (repair tool needed for full-scan/ carving; normal
   open MUST fail closed, never guess).
5. Load `ROOT_INDEX` → verify version/CRC chain → load
   `OBJECT_DIRECTORY` → check `txn_id` matches footer → binary-search
   objects on demand (streaming/partial load; MUST NOT require full
   materialization).

## 13. Versioning and compatibility

File carries: header `format_major/minor` + `DOCUMENT.bmoMajor/Minor`
(must match header) + `DOCUMENT.minMajor/minMinor` (oldest reader that
can open) + `requiredExtensions/optionalExtensions`.

* `0.x`: experimental, NO compat promise. Readers MUST warn but MAY open
  `0.1` if implemented.
* `1.x+`: same `major`, `file.minor <= reader.minor` → MUST open.
  `file.minor > reader.minor` → MAY open iff no unknown `CRITICAL`
  chunks and no unknown `requiredExtensions`; else fail
  `UPGRADE_REQUIRED`.
* Different `major` → MUST fail `INCOMPATIBLE_MAJOR` (migration tools
  outside this RFC MAY convert).
* Unknown chunk type: if `CRITICAL==1` → fail `UNKNOWN_CRITICAL`; else
  skip on read + preserve byte-exact on save (header+payload+trailer,
  original order preserved relative to other unknowns; known chunks MAY
  be reordered only if semantics unchanged — safest is to append new
  chunks and keep unknowns where the directory points).
* Unknown `requiredExtensions` entry → MUST fail `UNKNOWN_EXTENSION`.
  Unknown `optionalExtensions` → MAY ignore with degraded rendering.
* Unknown CBOR keys inside known maps → MUST preserve on round-trip
  (re-emit verbatim if possible, else retain decoded form canonically —
  MUST NOT drop).
* `chunk_version` newer than reader supports for a *known* type: treat
  as unknown-criticalness per that chunk's `CRITICAL` flag.

## 14. Limits (MUST enforce, fail `LIMIT_EXCEEDED` not overflow)

| Resource | Max | Note |
|----------|-----|------|
| File size / offset | 2^48-1 (~256 TiB) | u64 top 16 bits MUST be 0 |
| Chunk `stored_len` / `decoded_len` | 2^32-1 each | larger assets MUST split (§6.3) |
| Chunks per file | 2^32-1 | directory count is u32 |
| Directory entries | 2^32-1 | |
| Nesting depth (future model) | 256 | v0.1 CBOR nesting SHOULD be ≤64 |
| Secondary indexes per root | 255 | v0.1 usually 0 |
| Footer scan window (open) | 16 MiB | larger gaps need `bmo repair` |

Readers MUST pre-check lengths before allocating (no `malloc(decoded_len)`
without cap + streaming decompression with limit).

## 15. Security considerations

* No executable content: decoders MUST NOT execute bytes from the file.
  Fonts/images handled by model/renderer layers with their own sandboxing;
  container layer treats them as opaque bytes.
* DoS: enforce §14, stream large payloads, cap decompression ratio
  (RECOMMENDED max 100:1 per chunk unless `ARCHIVE` profile explicitly
  allows + user confirms).
* Crypto: use only §9 algorithms with standard libraries; random nonces
  from CSPRNG; constant-time tag comparison (library-provided); Argon2id
  params MUST be validated (mem/time/par within sane bounds).
* Signatures prove integrity + origin, NOT trust — key distribution out
  of scope for v0.1 (bring-your-own-PKI).
* Long-term archival: `ARCHIVE` flag + `SPEC` recommends storing
  `ZSTD/NONE` + unencrypted or password-independent copies + full
  `ASSET_TABLE` for self-description. Format docs (this RFC) are the
  archive contract, not any single binary.

## 16. Test vector: `hello.bmo` (deterministic, UNENCRYPTED, UNSIGNED)

Fixed inputs (so hashes are reproducible): `file_id = 00..01`
(15×`0x00` + `0x01`), `created_ms = 0`, `txn_id = 1`.

## 17. Conformance levels

* **Reader**: opens §16 + rejects corrupt magic/CRC/duplicate-ID/
  unknown-critical/unknown-required-extension/limit violations with the
  specified error codes; random-access reads without full scan.
* **Writer**: produces files passing Reader + deterministic CBOR +
  sorted directory + valid commit chain + `bmo validate` clean.
* **Round-trip**: Writer opening a file with unknown ancillary chunks +
  unknown optional extensions + unknown CBOR keys preserves them
  byte-identical (or CBOR-identical) after save.
* **Security**: correct `AUTH_FAILED` on tampered ciphertext/tag,
  correct signature verify/reject, no nonce reuse (statistical test),
  Argon2id params enforced.
* Test suites: `tests/conformance/{core,encoding,compression,encryption,
  compatibility}/` + `tests/golden/*` + fuzz corpus (`tests/fuzz/`).
  Golden files are pass/fail, not advisory.

## 18. Reference implementation guidance (non-normative)

Rust core (`bmo-core`) SHOULD expose C ABI (`bmo_document_open/
save/object_get/set/validate/...`) + WASM build of the same code; SDKs
(TypeScript first, then Python/C++/Kotlin/Swift) bind to it, never
reimplement the container independently (avoids spec drift — the DOCX
trap). Renderer/editor/converter/importers (DOCX/XLSX/PPTX/PDF) sit
above the core (see project README architecture diagram).

## 19. Deferred (explicitly NOT in RFC-0001)

Text engine (BiDi/RTL/shaping — RFC-0003), spreadsheet calc chain
(RFC-0005), presentation animations (RFC-0006), font embedding/subset
licensing, full security profiles (RFC-0007), extension registry
process (RFC-0008), conformance suite details (RFC-0009). This RFC
reserves their chunk-type ranges but defines no semantics.
